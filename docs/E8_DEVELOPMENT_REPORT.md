# E8 개발 결과 — 실제 실패 증거 연결과 평가 차단

기준일: 2026-10-27. 작업 후보: `0.8.0a1`, 미발행. 보존 기준: `v0.7.0a1` / `2edfb1230bd8519072845d9b9b0e2d4c42ab3837`.

**실제 개발 실패를 기존 지식 엔진에 연결했지만, 모든 후보가 반증되어 독립 전이 비교는 실행하지 않았다.** 도구 중립적인 수용, 기본 Native Hypothesis 수집, 출처·계보 검사와 최종 호출 전 차단은 제품 변경이다. 전이의 추가 가치, 기존 도구 대비 우위와 일반화는 입증하지 못했다. 기존 E7 결론·계약·archive를 소급 수정하지 않았다.

## B. 실제로 연결한 개발 근거

승인된 기존 E7 **v2 개발** 기록을 사용했다. v1의 잘못된 Oracle 기록은 학습에서 제외했고, 기존 최종 평가의 입력·답·계획을 Source나 새로운 블라인드 Target으로 재사용하지 않았다. 비공개 원본·입력·정답·원시 실행 로그는 이 보고서와 공개 패키지에 포함하지 않는다.

| 해당 Source의 실제 연결 | 개수 |
|---|---:|
| 적격 개발 관측 전체 | 371 |
| 기존 `from_failure_log()`의 결정론적 초기 prefix | 256 |
| 같은 Source의 추가 trusted DEVELOPMENT 관측 | 115 |
| 누락한 적격 관측 | 0 |
| 유효 실패 입력 | 5 |

다섯 입력을 서로 다른 다섯 결함으로 세지 않았다. 서로 다른 도구의 같은 관측도 독립 구현으로 세지 않았다. 기존 실제 관측들에서 같은 입력·결과가 반복된 근거를 `CACHED_OBSERVATION_REPLAY`로 수용했다. 이는 E8에서 새로 두 번 실행한 재현 영수증이 아니다. 기존 원본과 앞선 복원 세대의 해시는 그대로 보존했다.

기존 source/관측 각각 256개의 상한을 변경하지 않았다. 최초 256개 이후의 115개는 동일 Source origin의 기존 관측 API로 모두 연결했다. 결과를 보고 행·도구·시드를 바꿔 살아남는 후보를 찾지 않았다. 512개를 넘는 같은 context는 명시적으로 거부하며, 초기 prefix에 실패가 없으면 뒤의 양성만 골라 앞으로 옮기지 않는다.

기존 snapshot의 `independent_observations=115`는 개발 관측 행수라는 기존 필드명이다. 115개 모두 같은 Source이며 실제 독립 C는 0개다. 후보별 독립 양성·음성·contrastive 근거가 모두 비어 있음을 확인했다. 최초 Hypothesis 패키지 버전이 기존 영수증에 없다는 한계도 유지했다. 현재 설치 버전을 과거 실행 버전으로 대체하지 않았다.

## C. Source·Corroboration·Target 적격성

승인된 사용자 소유 5개 저장소에서 저장소별 최대 40개, 합계 182개 Git 이력과 함수 후보 18개를 정적으로 검토했다. 원본 작업 트리를 수정하거나 운영 코드를 실행하지 않았다. Git 객체를 기준으로 검토했으며 작업 트리의 dirty 상태는 확인 불가로 남겼다.

완전한 S→C→T 연구 연결의 수용은 0개다. 이 결과는 문서화된 과거 결함 자체가 없다는 뜻이 아니다. 현재 검토 범위에서 다음 근거를 함께 확보하지 못했다.

1. Source와 실제 구현 계보가 다른 **동일 계약의 별도 구현·검토된 Oracle**에서, 같은 구현의 독립 입력으로 얻은 양성·음성 예측 검증.
2. Source와 C에 사용하지 않았고 기존 최종 평가에도 소비되지 않은 Target의 정규화된 함수 정체성 및 사전 공개 계약 대응.
3. 평가자가 검증한 Target의 알려진 양성 재현·정상 대조 영수증과 해당 Oracle 검증.

수정 전후 버전, 같은 계보의 helper·wrapper, 이름·경로·해시 변경, 생산 도구 변경은 독립성의 근거가 되지 않는다. 일부 후보는 비표준 라이브러리 모델·callback·provider 실행을 필요로 해 승인된 순수 함수·표준 라이브러리 AST 범위에서 다루지 않았다. 검토한 이력·후보 예산 밖에도 독립 구현이 없다고 주장하지 않는다.

과거 결함을 향후 승인된 문제로 재현하면 `HISTORICAL_DEFECT_REDISCOVERY`로 분류한다. 해당 근거를 새 제로데이·새 생산 결함·새 블라인드 발견으로 표현하지 않는다.
